# 변경 검증

경로는 저장소 루트 기준이다. AGENTS.md의 현재 단계와 docs/verification.md를 읽고 실제 패키지 명령의 존재 여부를 확인한다. README는 사람을 위한 소개·사용법의 정확성을 검토할 때 참고하며 에이전트 상태 저장소로 사용하지 않는다. 커밋 작업에는 아래 커밋 규칙을 적용한다.

1. 변경에 해당하는 요구사항 ID와 완료 기준을 고른다. 미구현 단계는 구분한다.
2. 변경 위험에 맞는 기존 검사·승인된 테스트·직접 확인을 선택한다. 저장소의 필수 검사와 hook은 유지하되, 검사 통과 후 새 변경·실패·미해결 위험 없이 반복 실행하거나 새 테스트를 덧붙이지 않는다. 새 테스트가 필요하다고 판단되면 cv-review-tests에서 필요성과 코드 초안을 먼저 검토한다.
3. UI는 실제 빌드 화면의 뷰포트·키보드·장문·선택값 조건을 확인한다. 정적 검사만으로 화면 검증 완료를 주장하지 않는다.
4. 실패를 제품·테스트·환경 문제로 구분한다. 테스트 완화·삭제·snapshot 갱신을 임의로 하지 않는다.
5. 실행 명령·환경·실제 결과·증거·미검증 사항과 다음 검토 대상을 대화에서 보고한다. 변경 이유와 검증 요약은 커밋 본문에 남기며 별도 작업 로그를 누적하지 않는다.
6. 커밋할 때는 아래 규칙에 따라 변경을 묶고 검증한다. 테스트 코드 승인을 커밋 권한으로 대신하지 않는다.

하네스 단계는 문서·참조·frontmatter·링크가 대상이다. 스킬 인식과 실제 동작은 각각 증거가 있을 때만 완료로 기록한다. 앱·테스트가 없으면 미구현·미검증으로 보고한다.

요구사항 대응표는 확인할 동작을 정리한 것이며, 모든 행에 자동 테스트를 작성하라는 지시가 아니다. 기존 검사와 직접 실행으로 확인한 사항, 반복 회귀 검사를 위해 테스트로 남긴 사항, 아직 확인하지 못한 사항을 구분한다. 합의된 완료 조건을 충분히 확인했다면 새 테스트 없이도 해당 작업을 마칠 수 있다. 검증 방법을 간소화하는 것과 요구 동작을 확인하지 않은 채 완료로 기록하는 것을 혼동하지 않는다.

현재 단계 완료 후 다음 단계를 자동 실행하지 않는다.

## 커밋 규칙

### 단위와 완결성

- 파일 개수보다 변경 목적을 기준으로 나눈다. 기능과 이에 필요한 설정·문서·승인된 테스트는 함께 묶을 수 있다.
- 관련 없는 정리·전체 포맷 변경은 분리한다. 새 스킬과 이를 연결하는 문서처럼 서로 의존하는 변경은 함께 커밋한다.
- 각 커밋에서 참조 파일이 존재하고 해당 단계에서 실행 가능한 상태를 유지한다. 미구현 단계의 예정 경로·명령은 예정임을 명시한다.
- 승인 대기나 미구현 부분이 있으면 독립적으로 완료된 범위만 분리하고 전체 완료로 표현하지 않는다.

### 메시지

- 제목은 `유형: 구체적인 한글 변경 내용`으로 쓴다. 유형은 기능·수정·정리·문서·설정·도구·테스트·되돌림 중 선택한다. 정리는 동작을 바꾸지 않는 구조 개선이다.
- `수정 완료`, `작업 반영`, `업데이트` 같은 모호한 제목은 피하고 코드 식별자와 도구 이름은 원래 표기를 유지한다.
- 단순 변경은 제목만으로 충분하다. 동작·설정 변경에는 이유·실제 검증 결과를 본문에 적고 관련 검사 미실행 시 사유도 남긴다.

```text
설정: Astro와 Tailwind 개발 환경 구성
기능: 설정에서 이력서 데이터를 읽는 로더 추가
수정: 프로젝트 없는 경력의 빈 여백 제거
문서: 테마 설정 변경 방법 설명
```

본문에는 필요한 경우 `이유`, `검증`, `미검증` 항목을 짧게 쓴다. 예시의 검사 결과를 실제 실행 없이 복사하지 않는다.

### 검사와 이력

- 변경 목록과 staged diff를 검토하고 `git diff --cached --check`를 실행한다. 의도한 파일과 변경 부분만 포함한다.
- 필요한 타입·lint·승인된 테스트·빌드를 실행한다. 문서만 변경했다면 참조·내용과 해당 스킬 형식을 확인한다.
- 비밀값·실제 이력서 PDF·생성 파일·관련 없는 사용자 변경을 포함하지 않는다. 알려진 검사 실패를 숨긴 채 완료 커밋을 만들지 않고 원인을 해결하거나 사용자와 처리 방향을 합의한다.
- 승인된 구현 범위의 작업과 검증이 끝나면 로컬 커밋은 매번 재확인하지 않는다. 커밋 권한을 테스트 작성 승인이나 다음 단계 진행 승인으로 확대하지 않는다.
- 기본적으로 후속 커밋으로 수정한다. amend·rebase·강제 push 등 이력 변경과 원격 push는 별도 요청이 있을 때만 수행한다.
- 커밋 후 해시·한글 제목·검증 결과·남은 변경을 보고한다. 사용자 변경이 남아 있으면 깨끗한 작업 트리로 보고하지 않는다.

로컬 자동 검사를 실기기·프로덕션 검증으로 표현하지 않는다. 파일 형식 검사만으로 에이전트의 실제 규칙 준수를 보증하지 않는다.
