# 테스트 사전 검토

경로는 저장소 루트 기준이다. AGENTS.md, docs/verification.md를 읽고 대화에서 기존 승인 범위를 확인한다. 이전 승인 근거가 확인되지 않으면 추정하지 않는다.

## 테스트 추가 전 판단

먼저 이 테스트가 잡을 구체적인 회귀와 기존 검사로 잡지 못하는 이유를 확인한다. 충분한 기존 검사나 일회성 확인이 있으면 새 테스트를 제안하지 않아도 된다. 테스트 미추가 자체를 미완료로 취급하지 않는다.

- 직접 만든 변환·분기·오류 전파, 재현된 버그, 반복 확인이 필요한 중요한 계약은 회귀 테스트 후보로 삼는다. 현재 변경의 위험과 유지 비용을 비교해 필요한 사례만 고른다.
- Husky 연결·package script·일반적인 빌드 성공처럼 기존 명령으로 확인할 수 있는 설정은 직접 실행을 우선한다. 표준 import의 파일 누락 오류나 라이브러리 자체 동작을 재검증하기 위한 테스트는 기본적으로 추가하지 않는다.
- 실제 로더와 빌드의 연결은 의미 있는 확인 대상이지만, 이것만으로 매번 임시 프로젝트 복제·여러 하위 빌드·별도 Vitest 설정을 도입하지 않는다. 일회성 실패 빌드·산출물 확인으로 충분한지 먼저 판단한다. 통합 테스트는 단위 검사로 놓치는 중요한 경계의 회귀를 반복해서 잡아야 할 때 제안한다.
- 같은 규칙을 필드·계층마다 중복 검사하거나 구현 문자열·테스트 개수·coverage를 맞추는 사례를 늘리지 않는다. 최소 입력과 관찰 가능한 결과를 사용하고, 소수 사례를 위해 범용 helper·큰 fixture·snapshot을 만들지 않는다.

## 필요한 테스트의 사전 검토

1. 잡으려는 회귀, 기존 검증의 빈틈, 최소 입력과 기대 결과를 간결하게 제시한다. 관련 요구사항 ID가 있으면 연결한다.
2. 필요한 경우에만 fixture·mock·helper·새 도구의 이유와 유지 비용, 검증 한계를 설명한다. 단순한 사례에 정형화된 검토 표나 별도 설계 문서를 요구하지 않는다.
3. 실제 코드 초안 또는 diff를 대화에 제시하고 파일 반영 전에 명시적 승인을 기다린다.
4. 승인된 코드만 반영하고 승인 근거·범위를 대화에서 확인한다. 승인 로그 파일을 만들지 않고 다른 단계의 권한으로 확대하지 않는다.
5. 실행 결과를 보고한다. 수정·삭제·기대값 변경은 새 diff로 돌아간다.

테스트용 임시 파일·브라우저 평가 코드·fixture·기준 이미지도 동일한 대상이다. 파일을 먼저 쓰고 사후 검토로 대체하지 않는다. 응답 부재를 승인으로 해석하지 않는다. 승인과 무관한 독립 작업은 계속할 수 있다.

승인 전 상태는 ‘코드 검토 중’이다. 기존 승인된 테스트 실행에는 반복 승인받지 않는다.

필요성·시나리오·자동화 방향에 대한 합의만으로 코드 승인이 되지 않는다. 기존 CLI 명령 실행, 수동 화면 열람·키보드 탐색·스크린샷 확인은 테스트 코드 작성과 구분한다. 일회성 확인이라는 이름으로 새 테스트 코드나 fixture의 사전 검토를 우회하지 않는다.
